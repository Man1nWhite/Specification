## A. Findings that change the output

### A1 (High) — the Python engine silently drops line items whose quantity is a formula it cannot evaluate

`generate_tkp.py:176-239` (`_eval_cell`) understands exactly two formula shapes: a single
cross-sheet reference (`='Лист'!C2`) and `SUMIF(`. Everything else falls through to
`return raw_val` — the **cached** value of the `data_only=True` workbook (`:239`), which is
`None` when the cache is absent. `_parse_numeric_qty()` then turns `None`, a formula string
or an Excel error into `0.0` (`:242-256`), and `_collect_section_items()` skips the row
because `qty > 0` fails (`:284`). No exception, no warning, exit code 0.

Measured, same edits fed to both engines:

| quantity typed into G | VBA (as Excel would) | Python |
|---|---|---|
| `=2+3` | row emitted, qty `5` | **row missing** |
| `=SUM(1,2)` | row emitted, qty `3` | **row missing** |
| `='Конфигуратор лицензии'!J27`, where `J27` is `=3*2` | row emitted, qty `6` | **row missing** |
| `='Конфигуратор лицензии'!J27`, where `J27` is a literal `5` | qty `5` | qty `5` ✓ |
| `ROUNDUP(SUMIF(...)/10,0)` (real ЗИП formula) | computed | computed ✓ |

Why this is High rather than cosmetic: the whole point of the "no Excel, no COM" path is to
produce the deliverable on a machine without Excel. The failure mode is a *missing line in
Appendix 3*, indistinguishable from "the engineer did not order it", and the run reports
success with a smaller item count that nobody can compare against anything.

Preconditions where the cached value is absent or stale (all realistic):
the file was last written by a tool that does not cache formula results (openpyxl, some
LibreOffice configurations); calculation is set to manual, so the cache predates the last
edit; or the caller uses the library API with an in-memory `Workbook`
(`read_tkp_data(wb)` at `:311`), which by construction has no cache for cells the caller
touched.

Recommendations (in order):
1. When a formula cell reaches `return raw_val` and `raw_val` is `None`, **do not silently
   emit 0** — collect it and fail the run with the sheet/row, or at minimum print the
   offending cells to stderr. Silent 0 is the bug; the missing formula support is the
   limitation.
2. When `raw_val` is a numeric cache, trust it (that is what Word/Excel would show) rather
   than requiring the two whitelisted shapes.
3. Add a differential test over the **whole demo dataset** (both engines, no per-cell
   edits), which is the gap that let this survive: today only
   `test_total_and_margin_rows…`, `test_hash_prefixed…` and the demo case in
   `test_generation_groups…` compare the engines, all on hand-written literals
   (`tests/test_tkp.py:1034` `_run_both`).

### A2 (Medium) — the CLI silently substitutes fabricated demo data

`main()` always passes `use_demo_if_empty=True` (`generate_tkp.py:895`). With a workbook
that has no `G > 0` rows — the normal state of a user who forgot to fill quantities — the
run injects `populate_demo_workbook()` (`:718`): the customer becomes
«ООО «Газпром трансгаз Томск»», the object «АСУ ТП компрессорного цеха КС-4», and 16
invented line items. Output:

```
$ python generate_tkp.py -e empty.xlsm -o out.docx
Документ сохранен: /tmp/…/out.docx (разделов: 7, позиций: 16)
```

Nothing in that line says "demo". The document is fully populated and plausible. The VBA
equivalent refuses: «Нет позиций с количеством больше нуля. Заполните столбец G…»
(`Module1.bas:33-36`).

Recommendation: make the demo explicit — either `--demo` opt-in, or refuse with the same
message as the macro, or at minimum print
`ВНИМАНИЕ: в книге нет позиций, подставлены демонстрационные данные` to stderr and write a
marker (e.g. «ДЕМО» in the title bookmark) into the document. README already documents the
behaviour, but documentation is not a guard against shipping a fake proposal.

### A3 (Medium) — missing or renamed bookmarks are ignored

`set_bookmark_text()` returns `bool` (`:459`), and all five call sites discard it
(`:846-855`). If the template is revised and a bookmark disappears, the generator writes a
document anyway: titles keep the template placeholders and `populate_spec_table()` falls
through the `if starts and body is not None:` branch (`:668`), so the specification table is
appended at the **end of the document** instead of at `Spec_Table` — no heading, no
«Приложение 3».

Verified by stripping every bookmark from a copy of `ТКП_шаблон.dotx` and generating:
`generate_tkp(...)` returned normally and wrote the file. In the result the specification
table is the **last block of the body** (immediately before `w:sectPr`, i.e. after
«Термины и сокращения») instead of sitting at Appendix 3, and the title fields still read
«Номер», «Заказчик», i.e. the placeholders were never replaced. The VBA path raises `5941`
and closes the document with a message box.

Recommendation: after filling the bookmarks, assert that `Num`, `Customer`, `Object` and
`Spec_Table` were found (and that the table was actually inserted into the body), raising
`ValueError` with the missing names. `Subject` may stay optional — the template may
legitimately omit it.

### A4 (Medium) — quantity parsing/formatting depends on the machine locale

- VBA parses with `IsNumeric` / `CDbl` (`Module1.bas:236-237`) and renders with
  `ЧистыйТекст` → `CStr` (`:85`). Both are locale-sensitive.
- Python parses with an explicit `,`→`.` replacement (`:250`) and renders with
  `format_qty()` → always `.` (`:119-130`).

Consequences, all reproducible:

| input | VBA on ru-RU Excel | VBA on en-US Excel | Python |
|---|---|---|---|
| text `"3,5"` in G | qty `3,5` | **row dropped** (`IsNumeric` false) | qty `3.5` |
| numeric `2.5` in the Word table | `2,5` | `2.5` | `2.5` |

The last row matters for a Russian-language commercial proposal: the Python generator emits
a dot in a document where every other number uses a comma, and the two engines produce
different text for the same input. The suite cannot see it because `_run_both` compares
*preview rows* (raw numbers), never the Word text, and `pyopenvba` is not locale-aware, so
it cannot reproduce either VBA behaviour.

Recommendation: format quantities explicitly in both engines, e.g. VBA
`Format$(qty, "0.############")` then `Replace$(…, ",", ".")`, and Python
`format_qty()` deciding the separator once. Whichever convention is chosen, it should be
asserted in a test that reads the generated table cell, not the preview.

## B. Low-severity findings

### B1 — block order differs between engines
The VBA macro walks the sheet once, in row order (`ОбработатьЛист`, `:205-283`); Python
rescans each cabinet sheet once per block and therefore always emits block 1 → 2 → 3
(`generate_tkp.py:351-380`). With a sheet whose captions are physically reordered, the
previews diverge (verified: VBA emitted «Шкафное оборудование ПТК (шкаф 1)» first, Python
«Оборудование ПТК (шкаф 1)»). Titles stay attached to their items, so nothing is corrupted,
but the two documents are not the same document. Cheap fix: scan once in Python, deriving
sections in row order like the macro.

### B2 — an unrecognised caption drops the block silently
`_block_from_caption()` (`:139-146`) / `НомерБлока()` (`Module1.bas:302-312`) recognise only
`НВТ`, `Эксара`/`ИнСАТ` and `3-х поставщиков`. Any other caption — including a typo in one
of those — sets the block to 0, and every following row is skipped in **both** engines,
while `has_captions` stays `True`, so the row-range fallback never applies. A typo therefore
deletes a section from the proposal without a trace. Recommendation: treat an
unrecognised `Спецификация …` caption as an error (or a warning naming the caption).

### B3 — the running header loses its `REF Num` field
The template header holds `REF Num`; `set_bookmark_text()` replaces the field with static
text (asserted by `test_python_build_from_dotx_template`), so editing the number on page 1 in
Word no longer updates the header — which is exactly what the field was for. Defensible (the
header must not depend on a field updated at print time), but it is a behavioural difference
worth one line in the README.

### B4 — an empty even-page header part is created
Section 0 cannot be "linked to previous", so touching `section.even_page_header`
(`:853-855`) materialises an empty `word/header3.xml` and an `even` `headerReference`.
Harmless today because `w:evenAndOddHeaders` is absent from `word/settings.xml`, but enabling
odd/even headers later would blank the running head on even pages. Guard with
`if hdr.is_linked_to_previous or not hdr._element…`.

### B5 — runtime dependencies are only lower-bounded
`requirements-dev.txt` pins `pyOpenVBA`, `lxml` and `ruff` but leaves
`openpyxl>=3.1.0` and `python-docx>=1.1.0`. The file's own comment says the pins exist so
"local runs and CI agree"; python-docx is currently resolved to 1.2.0 and its header/section
API is precisely what A3/B4 depend on. Pin both (or bound them, `python-docx>=1.1,<2`).

### B6 — Python version coverage
CI runs 3.11 only; `ruff.toml` says `target-version = "py310"` and `README.md` promises
Python 3.10+. The code uses `zip(..., strict=True)` and PEP 604 unions, so 3.10 should work,
but it is untested. Add a 3.10 leg to the matrix.

### B7 — dead lint configuration
`ruff.toml` ignores `PT009`, `PT018`, `PT027` under `[lint.per-file-ignores]`, but the `PT`
(flake8-pytest-style) ruleset is not in `select`. The entries do nothing; either select `PT`
or drop the ignores.

### B8 — author metadata still in the template
`docProps/core.xml` of `ТКП_шаблон.dotx` still carries `<dc:creator>ABagdasaryan</dc:creator>`
and `<cp:lastModifiedBy>`; `docProps/app.xml` still names `ТКП_шаблон 1.dotx` as the source
template. This contradicts `AUDIT.md`'s claim that M2 ("personal data committed in the binary
assets") was fixed — the `.xlsm` was cleaned, the `.dotx` was not. Strip both in
`_set_document_title()`/`patch_template()` so the sync tool enforces it.

### B9 — `AUDIT.md` is stale
It reports "6 → 11 tests" (there are 31), "3 high, 3 medium, 6 low, every fix verified", and
marks M2 Fixed. It is not referenced from `README.md`, so a reader cannot tell it describes a
superseded revision. Either move per-round audits under `docs/audits/` with the revision in
the filename, or fold the resolution table into `README.md` and delete the file.

### B10 — direct pushes to `main` are not gated
The only failed run in the repository's history is `6b5e1b7` "Add files via upload"
(2026-10-25, a `.dotx` uploaded through the web UI straight to `main`) — the workflow caught
it, nothing prevented the push. Branch protection with "require status checks" for the
`tests` workflow would have. (I could not read the protection settings: the token gets
`403 Resource not accessible by integration`, so this is stated from the history, not from
the configuration.)

### B11 — cross-engine coverage is thin
`tests/test_tkp.py` has 31 tests, but only three compare the two engines, all through
`_run_both()` with literal cell values (`:1034`). There is no end-to-end differential over
the demo dataset, no test for `main()`/CLI behaviour, `find_default_workbook()`,
`update_preview_sheet()`, the missing-bookmark path, or `sync_assets`' *workbook*
idempotency (verified manually here). A1, A4 and B1 all live in that uncovered space.

### B12 — `sync_assets.py` refuses to run after a preview exists
`patch_preview_sheet()` raises `ValueError("The preview sheet is not empty; refusing to
erase it")` unless the sheet is at `A1:G3` (i.e. freshly initialised). That is the right
default — it refuses to destroy data — but the workflow in `README.md`
(«После изменения VBA, шаблона или структуры предпросмотра выполните
`python tools/sync_assets.py`») breaks for anyone who has pressed `Alt+F8 →
ОбновитьСпецификациюТКП` since. Mention the prerequisite in the README (clear `Спец_ТКП`
first), or have the tool clear the generated rows itself when it can prove the sheet holds
only preview data.

## C. Suggested order of work

1. **A1** — turn silent quantity loss into a hard failure plus a dataset-level differential
   test. Smallest change with the largest safety gain.
2. **A3** — fail loudly on missing bookmarks; this is three assertions and removes the only
   way to produce a misbuilt document without noticing.
3. **A2** — make the demo explicit.
4. **A4** — one formatting decision, applied in both engines and asserted on the Word text.
5. **B5/B8/B9/B12** — housekeeping that keeps the next audit cheap: pin the two libraries,
   strip metadata in the sync tool, move the stale report, document the preview prerequisite.
6. **B1/B2/B4/B6/B7/B10/B11** — as capacity allows.

Each of A1–A4 and B1 is reproducible with the harness pattern in
`tests/test_tkp.py:1034` (`_run_both`): apply identical edits to both engines, compare
`normalise_preview_rows(...)`; for A4 compare the generated Word cell text instead.
