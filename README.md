# Генератор ТКП — Приложение 3 «Спецификация оборудования»

## Файлы проекта

Для работы генератора используются:

- `Gen_TKP.xlsm` — книга Excel с макросами;
- `ТКП_шаблон.dotx` — единственный Word-шаблон с нужными закладками; свойство документа «Название» в нём — `ТКП`, поэтому документ, созданный из шаблона, называется «ТКП» (видимый заголовок на первой странице — «Технико-коммерческое предложение»);
- `Module1.bas` — редактируемый исходный код VBA;
- `generate_tkp.py` — автономный генератор на Python;
- `tools/sync_assets.py` — синхронизация исходников VBA, книги Excel и шаблона;
- `tests/test_tkp.py` — автоматические проверки.

`README.md`, `LICENSE`, `requirements.txt` (зависимости генератора) и `requirements-dev.txt` (плюс интерпретатор VBA и линтер для разработки) — документация, лицензия и зависимости. Аудиты лежат в `docs/audits/`. Исходный `.docx`, копии шаблона `.docx` и заранее сгенерированный результат в репозитории не хранятся. Python-генератор создает результат при запуске.

## Как пользоваться в Excel/Word (Windows)

1. Положите `Gen_TKP.xlsm` и `ТКП_шаблон.dotx` в одну папку. Откройте книгу в **Microsoft Excel для Windows** и разрешите макросы.
2. Заполните номер ТКП, заказчика, объект и предмет на листе `Наценки-Скидки` в ячейках **C2–C5** (они подставляются в закладки `Num`, `HeaderNum`, `Customer`, `Object`, `Subject`). Заполните позиции и количества на листах `SW(w.o.VAT)` (ПО), `1`–`17` (шкафы 1–17) и `Spare parts` (ЗИП).
3. Для проверки списка нажмите **Alt+F8 → ОбновитьСпецификациюТКП**: предпросмотр появится на листе `Спец_ТКП`. Либо нажмите **Alt+F8 → СформироватьТКП**: список обновится автоматически, а в Word откроется новое ТКП с заполненными реквизитами и таблицей Приложения 3 на месте закладки `Spec_Table`.

## Структура таблицы в Приложении 3

Для каждой позиции берутся столбцы **C** (наименование и техническая характеристика), **D** (позиция / артикул), **F** (ед. изм.) и **G** (количество). В спецификацию попадают только строки с количеством **G > 0**. Если формула в столбце **C** содержит `#REF!` и возвращает пустую строку или `"0"`, при `G > 0` и заполненном артикуле в **D** в наименование подставляется значение из **D**. Цены, себестоимость, наценки, строки «Итого...» и работы в Приложение 3 не переносятся.

Разделы включаются в таблицу только при наличии в них хотя бы одной позиции с `G > 0`:

- Заголовок каждого раздела выделяется **жирным шрифтом**, имеет сквозную нумерацию (`1.`, `2.`, `3.` ...); в столбце 4 (`Ед. изм.`) указывается `Компл.`, в столбце 5 (`Кол-во`) — `1`. Разделы идут в том порядке, в котором стоят на листе: если два заголовка «Спецификация…» одного блока поменяны местами, в документе они тоже идут в порядке строк.
- Внутри каждого раздела позиции нумеруются заново (`1.`, `2.`, `3.` ...) обычным шрифтом.
- Порядок разделов:
  1. **Программное обеспечение** — все позиции с `G > 0` с листа `SW(w.o.VAT)`.
  2. **По каждому задействованному шкафу (листы `1`–`17`):**
     - Блок 1 («Спецификация оборудования НВТ») → `Оборудование ПТК (шкаф N)`.
     - Блок 2 («Спецификация оборудования Эксара») → `Телекоммуникационное оборудование для АСУ ТП (шкаф N)`.
     - Блок 3 («Спецификация оборудования 3-х поставщиков») → `Шкафное оборудование ПТК (шкаф N)`.
  3. **ЗИП** — все позиции с `G > 0` с листа `Spare parts`.

Количество в **G** читается одинаково в обеих реализациях и не зависит от локали Windows: числовое значение — как есть, текст — только в обычной десятичной записи с точкой или запятой (`3,5`, `0.25`). Всё остальное (`1_000`, `inf`, `1e3`, `٢`) количеством не считается. В документе количество печатается с десятичной запятой и не более чем шестью знаками после неё: `2,5`, а не `2.5`.

Заголовок «Спецификация …» в столбце **B** должен называть один из разделов — «НВТ», «Эксара»/«ИнСАТ» или «3-х поставщиков». Любой другой текст (в том числе опечатка вроде «3-х **поставшиков**», которая встречается на листе `Наценки-Скидки` в ячейках `H5` и `H8`) — ошибка: обе реализации останавливаются и ничего не переносят.

Если формулу в **C**, **D**, **F** или **G** не удалось вычислить, а сохранённого значения в книге нет (книга не пересчитана в Excel или открыта в памяти), генератор сообщает адрес ячейки и останавливается: пустое место в спецификации выглядело бы как «ничего не нужно поставить». Флаг `--allow-unresolved` превращает остановку в предупреждение. Столбец **B** в эту проверку не входит: он определяет только группировку и в документ не попадает.

## Устройство шаблона

`ТКП_шаблон.dotx` — титульный лист, параметры предложения с условиями, десять
приложений и страница «Термины и сокращения». Правила, которые поддерживает
`tools/sync_assets.py` и проверяют тесты:

- **Кегль текста — 12 pt** во всём документе: прямое форматирование, стили и
  нумерация, которые использует документ. Прежние 10 pt больше не применяются,
  колонтитулы сохраняют свой мелкий кегль. Таблица Приложения 3, которую строят
  генераторы, набирается тем же 12 pt.
- **Одно исключение — таблица этапов в Приложении 8**: она набрана 11 pt целиком.
  Четыре столбца наименований и сроков при 12 pt переносятся некрасиво, а сама
  таблица — график, а не текст, поэтому размер оставлен меньше основного.
  `tools/sync_assets.py` сознательно не поднимает его до 12 pt, а тест это
  закрепляет.
- **Колонтитул** читается как «Технико-коммерческое предложение № …» и берёт
  номер из строки «Номер» на первой странице: в шаблоне там поле `REF Num`, а
  генераторы подставляют значение из ячейки `C2` листа `Наценки-Скидки`
  (знак «№» добавляется сам, поэтому «№ №» появиться не может).
- **Страница с параметрами предложения** держится двух блоков: «Исходные данные
  и допущения» — одно предложение, внутри которого назван документ-основание с
  номером, датой и ревизией, и «Не входит в объём предложения» — список без вводной
  строки: датчики и исполнительные механизмы, внешние кабели, строительная
  часть, АРМ и серверы, ИБП, проектная документация стадий «П» и «Р»,
  метрологическая аттестация, экспертиза промышленной безопасности,
  мероприятия по КИИ и требованиям ФСТЭК России, согласования в надзорных
  органах. Раздела «Обязательства Заказчика» здесь нет: требования к площадке,
  пропуска и подготовка технологической среды сформулированы один раз —
  в Приложении 5, рядом с работами, которых они касаются.

  > **Известный пробел:** срок согласования РКД Заказчиком (10 рабочих дней) и
  > обязанность обеспечить технологическую среду к началу ПНР в документе
  > отсутствуют — см. [аудит от 2026-10-28](docs/audits/2026-10-28.md), раздел
  > N8. До правки шаблона эти условия надо вносить в предложение вручную.
- **Общий срок** в таблице параметров: строка «Общий срок реализации проекта —
  35 недель» стоит после этапов и перед строками «ИТОГО».
- **Условия оплаты**: второй платёж за оборудование привязан к подписанию УПД,
  аванс по этапу работ платится за 7 календарных дней, счёт по обучению
  выставляется после подписания акта. **Условия поставки** говорят только о
  поставке оборудования на склад Заказчика.
- **Приложения 9 и 10** — описание ПТК АРКС400 и страница о компании. У обоих
  стоит метка «Приложение N» с тем же полем `SEQ App`, что и у остальных
  приложений, и обе строки есть в списке приложений, поэтому номера
  пересчитываются сами. Страница «Термины и сокращения» приложением не является
  и номера не получает.
- **Приложение 4** («Перечень передаваемой документации») — список из 22
  документов без группового заголовка в таблице: структурная схема, схемы
  соединений внешних проводок, принципиальные схемы и схемы подключений, чертежи
  общего вида шкафов, ведомость покупных изделий, ПМИ, протоколы ЗПИ и ПСИ,
  описание ППО, руководства оператора и администратора, инструкция по ТО,
  формуляр (паспорт), ведомость ЗИП, протоколы электроизмерений, исполнительная
  документация, паспорта и сертификаты на покупное оборудование и акт
  выполненных ПНР. Общие строки, дублировавшие конкретные документы, убраны.
- **Приложение 5** («Монтажные работы») перечисляет состав работ (разгрузка и
  перемещение к месту установки, монтаж шкафов, маркировка шкафов и
  оборудования, подключение питания шкафов, заземление шкафов, межшкафные
  связи, ЛВС и АРМ, сборка кроссов, маркировка кабелей), требования к готовности площадки и
  примечание о том, что в объём работ не входит. Блок готовности площадки идёт
  без собственного заголовка: его вводит фраза «К началу монтажных работ
  Заказчик обеспечивает:», как и остальные списки документа, а сам список
  короткий — основания и фальшпол, контур заземления, питание 1ф/3ф, освещение,
  пропускной режим, бытовки, места складирования.
- **Приложение 8** («Календарный план») показывает диаграмму Ганта сразу под
  таблицей этапов, без заголовка и подписи: всё приложение и есть календарный
  план. В таблице 35 колонок по числу недель, полосы этапов и итоговая строка
  «Общий срок реализации проекта — 35 недель». Шкала недель набрана мельче
  основного текста (8 pt), иначе номера недель не помещаются в колонку; названия
  этапов остаются 12 pt. Таблица занимает 4949 + 35 × 275 = 14574 twips — это
  больше полосы набора книжной страницы (9780 twips), поэтому диаграмма стоит
  на отдельной странице с альбомной ориентацией: разрывы раздела до и после неё
  (тип `nextPage`), сама диаграмма — единственное содержимое раздела, а
  Приложение 9 начинается снова на книжной странице. В альбомной ориентации с
  теми же полями остаётся 14712 twips, так что сетка помещается целиком.
- **Сертификация** начинается связкой «ПТК АРКС400 входит в состав системы
  «МИРТС»», дальше идут номера Госреестра, сертификатов и реестров.
- **Последняя страница** — «Термины и сокращения»: ПТК, ППО, РКД, УСО, ЗПИ,
  ПСИ, АРМ, КИИ и остальные сокращения документа.

Блоки страницы с параметрами, список приложений вместе с метками «Приложение N»,
примечание к монтажным работам, требования к готовности площадки, колонтитул и
диаграмма Ганта синхронизация приводит к тексту констант из
`tools/sync_assets.py`: лишние пункты уходят, недостающие появляются, а
формулировки берутся из констант. Именно поэтому сокращённая редакция шаблона —
источник истины: повторный запуск инструмента ничего в нём не меняет (это
проверяет тест, сверяя все части файла байт в байт). Остальные блоки (строка
общего срока, страница терминов) добавляются один раз и не перезаписываются,
чтобы правки документа вручную не терялись. Шаблон прошлой ревизии инструмент
тоже приводит к текущему содержанию, но может оставить лишний пустой абзац:
чистая копия текущего шаблона — эталон.

## Автономная сборка на Python (без Excel/Word COM)

Установите зависимости и запустите генератор:

```bash
python -m pip install -r requirements.txt   # только генератор
python generate_tkp.py
```

Для разработки и тестов понадобится больше:

```bash
python -m pip install -r requirements-dev.txt   # + pyOpenVBA и ruff
```

По умолчанию скрипт берет `Gen_TKP.xlsm` (если его нет — `Gen_TKP.xlsx`) и `ТКП_шаблон.dotx` из папки проекта и создает `Технико-коммерческое предложение.docx`. Используемая книга печатается в выводе.

Пустая книга — ошибка, а не повод собрать пустое предложение: если ни у одной позиции количество `G` не больше нуля, скрипт сообщает об этом и завершается с кодом `2`, не создавая файл. Флаг `--demo` собирает документ на демонстрационных данных — только в памяти, исходная книга не изменяется, а в выводе предупреждение повторено. Код `2` скрипт возвращает и при любой другой остановке: нет шаблона или закладки в нём, файл не открывается, формула без сохранённого значения.

При необходимости можно указать файлы явно:

```bash
python generate_tkp.py --excel путь/книга.xlsm --template путь/шаблон.dotx --output путь/результат.docx
```

Файл записывается во временное имя рядом с целевым и только потом переименовывается: прерванный запуск не оставляет недописанный документ, а занятый Word'ом файл даёт понятную ошибку.

## Синхронизация, тесты и проверки

После изменения VBA, шаблона или структуры предпросмотра выполните:

```bash
python tools/sync_assets.py
git status            # должна измениться только Gen_TKP.xlsm
python -m ruff check .
python -m unittest discover -s tests -v
```

Правила линтера зафиксированы в `ruff.toml`. Тесты сверяют две реализации одного
алгоритма: VBA-макрос выполняется в памяти через `pyopenvba`, генератор на Python
считает те же данные, и результаты сравниваются. Три теста сверяют отдельные
правила (пропуск «Итого» и «МАРЖА», значения, начинающиеся с `#`, текст вместо
числа в количестве), один — весь демонстрационный набор целиком, строка в строку.
Это удерживает обе реализации от расхождения.

GitHub Actions запускает линтер, этот набор тестов на Python 3.10 и 3.12 и
проверку закреплённых зависимостей (`pip-audit`) при push и создании pull request.

Скрипт синхронизации обновляет `ТКП_шаблон.dotx`, лист предпросмотра в `Gen_TKP.xlsm` и встроенный VBA-модуль, а также очищает поля автора (`dc:creator`, `cp:lastModifiedBy`) в обоих файлах: имя того, кто сохранял файл, не должно уезжать к заказчику. Он не создает копии `.docx` и демонстрационные результаты. Выходной файл `Технико-коммерческое предложение.docx` исключен из Git и может быть создан повторно командой `python generate_tkp.py`.

Перед запуском синхронизации очистите лист `Спец_ТКП` в книге: шаг, который ведёт предпросмотр, отказывается перезаписывать непустой лист.
